STEP 2: FIX SQL INJECTION VULNERABILITIES
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    query = f"SELECT * FROM users WHERE username='{username}' AND password='{password}'"
    cursor.execute(query)

SECURE CODE (✅):
    cursor.execute(
        "SELECT * FROM users WHERE username=? AND password=?",
        (username, password)
    )

EXPLANATION:
- Use parameterized queries with ? placeholders (SQLite syntax)
- The database driver handles proper escaping automatically
- User input is treated as data, not SQL code
- Prevents SQL injection attacks completely

IMPLEMENTATION STEPS:
1. Replace all f-strings in SQL queries with parameterized queries
2. Move user input to the second parameter tuple
3. Use ? for SQLite, %s for MySQL/PostgreSQL
4. Test with special characters: ', ", --, ;

AFFECTED LOCATIONS:
- Line 38-40: /login route
- Line 62-68: /profile route  
- Line 76-82: /api/data route

VULNERABLE CODE (❌):

SECURE CODE (✅):

STEP 4: FIX CROSS-SITE SCRIPTING (XSS)
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    query = request.args.get('q', '')
    return f"<h1>Search Results for: {query}</h1>"
    
    Attack: /search?q=<script>alert('XSS')</script>
    Result: JavaScript executed in user's browser

SECURE CODE (✅) - Option 1: Using escape()
    from flask import escape
    
    query = request.args.get('q', '')
    return f"<h1>Search Results for: {escape(query)}</h1>"
    
SECURE CODE (✅) - Option 2: Using Jinja2 Templates (RECOMMENDED)
    from flask import render_template
    
    @app.route('/search')
    def search():
        query = request.args.get('q', '')
        return render_template('search.html', query=query)
    
    # In templates/search.html:
    <h1>Search Results for: {{ query }}</h1>
    
    (Jinja2 auto-escapes by default with {{ }} syntax)

EXPLANATION:
- HTML escaping converts dangerous characters: < > " ' &
- <script> becomes &lt;script&gt; (rendered as text, not code)
- Jinja2 templates with {{ }} syntax auto-escape
- Always escape user input when displaying in HTML

IMPLEMENTATION STEPS:
1. Install Jinja2 (comes with Flask)
2. Create templates/ directory
3. Create search.html template with {{ query }} syntax
4. Or use escape() function for inline HTML
5. Test with payloads: <script>, <img onerror>, javascript:

STEP 5: IMPLEMENT AUTHENTICATION & AUTHORIZATION
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    @app.route('/profile/<user_id>')
    def profile(user_id):
        db = get_db()
        cursor = db.cursor()
        cursor.execute(f"SELECT * FROM users WHERE id={user_id}")
        # No authentication check - anyone can view any profile!

SECURE CODE (✅):
    from functools import wraps
    from flask import session, redirect
    
    def login_required(f):
        @wraps(f)
        def decorated_function(*args, **kwargs):
            if 'user_id' not in session:
                return redirect('/login')
            return f(*args, **kwargs)
        return decorated_function
    
    @app.route('/profile/<user_id>')
    @login_required
    def profile(user_id):
        # Verify user can only access their own profile
        if int(user_id) != session.get('user_id'):
            return "Unauthorized", 403
        
        db = get_db()
        cursor = db.cursor()
        cursor.execute("SELECT * FROM users WHERE id=?", (user_id,))
        # ... rest of code

EXPLANATION:
- login_required decorator checks if user is authenticated
- Authorization check ensures user can only access own data
- Session variables store user identity after login
- Redirect unauthenticated users to login page

IMPLEMENTATION STEPS:
1. Create login_required decorator
2. Add decorator to all protected routes
3. Implement authorization checks (own data only)
4. Use session variables for user identity
5. Test unauthorized access attempts

STEP 6: FIX UNSAFE FILE UPLOAD
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    @app.route('/upload', methods=['POST'])
    def upload():
        file = request.files['file']
        file.save(os.path.join('/tmp', file.filename))
        # No validation - accepts any file!
        # No size limit - allows large files!
        # Path traversal possible!

SECURE CODE (✅):
    from werkzeug.utils import secure_filename
    import uuid
    
    ALLOWED_EXTENSIONS = {'txt', 'pdf', 'png', 'jpg', 'jpeg'}
    MAX_FILE_SIZE = 5 * 1024 * 1024  # 5MB
    UPLOAD_FOLDER = '/tmp/uploads'
    
    def allowed_file(filename):
        return '.' in filename and filename.rsplit('.', 1)[1].lower() in ALLOWED_EXTENSIONS
    
    @app.route('/upload', methods=['POST'])
    @login_required
    def upload():
        file = request.files['file']
        
        # Validation 1: File exists
        if not file or file.filename == '':
            return "No file selected", 400
        
        # Validation 2: File extension
        if not allowed_file(file.filename):
            return "File type not allowed", 400
        
        # Validation 3: File size
        file.seek(0, os.SEEK_END)
        if file.tell() > MAX_FILE_SIZE:
            return "File too large", 400
        
        # Safe file handling
        filename = secure_filename(file.filename)
        unique_name = f"{uuid.uuid4()}_{filename}"
        filepath = os.path.join(UPLOAD_FOLDER, unique_name)
        
        os.makedirs(UPLOAD_FOLDER, exist_ok=True)
        file.seek(0)
        file.save(filepath)
        return "File uploaded"

EXPLANATION:
- secure_filename() removes path traversal attempts
- Whitelist allowed file extensions
- Validate file size before saving
- Generate unique filenames to prevent overwrites
- Store outside web-accessible directory

IMPLEMENTATION STEPS:
1. Define ALLOWED_EXTENSIONS set
2. Define MAX_FILE_SIZE constant
3. Validate file existence
4. Check file extension against whitelist
5. Check file size before save
6. Use secure_filename() 
7. Generate unique filename with uuid
8. Create upload directory if not exists
9. Save to secure location
10. Test with: large files, blocked extensions, path traversal

STEP 7: FIX UNSAFE DESERIALIZATION
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    @app.route('/deserialize', methods=['POST'])
    def deserialize():
        data = request.form.get('data')
        obj = pickle.loads(data)  # CRITICAL: Remote Code Execution!
        return str(obj)

SECURE CODE (✅) - RECOMMENDED: Use JSON instead
    import json
    
    @app.route('/deserialize', methods=['POST'])
    def deserialize():
        try:
            data = request.form.get('data')
            obj = json.loads(data)
            return json.dumps({"result": str(obj)})
        except json.JSONDecodeError:
            return "Invalid JSON", 400

SECURE CODE (✅) - ALTERNATIVE: Restricted Unpickler
    import pickle
    import io
    
    class RestrictedUnpickler(pickle.Unpickler):
        def find_class(self, module, name):
            # Whitelist safe classes only
            if module == "builtins" and name in ("list", "dict", "str", "int"):
                return getattr(__builtins__, name)
            raise pickle.UnpicklingError(f"Forbidden: {module}.{name}")
    
    def loads(data):
        return RestrictedUnpickler(io.BytesIO(data)).load()

EXPLANATION:
- pickle.loads() is unsafe because it can execute arbitrary code
- JSON is safe alternative for most data serialization
- RestrictedUnpickler limits which classes can be deserialized
- Never deserialize untrusted data unless absolutely necessary

IMPLEMENTATION STEPS:
1. Replace pickle with JSON (preferred)
2. Update frontend to send/receive JSON
3. Or implement RestrictedUnpickler if pickle necessary
4. Add error handling for invalid JSON/pickle
5. Test with various payloads

STEP 8: DISABLE DEBUG MODE IN PRODUCTION
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    if __name__ == '__main__':
        app.run(debug=True)  # Debug mode enabled - exposes info!

SECURE CODE (✅):
    import os
    from dotenv import load_dotenv

EXPLANATION:
- Debug mode shows full stack traces with source code
- Interactive debugger can be exploited
- Environment variables control debug per environment
- Development: FLASK_ENV=development (debug=True)
- Production: FLASK_ENV=production (debug=False)

IMPLEMENTATION STEPS:
1. Add FLASK_ENV to .env file
2. Update app.run(debug=...) to use environment variable
3. Ensure FLASK_ENV=production on production server
4. Test: no stack traces shown for errors in production
5. Use proper logging instead of debug output

STEP 10: ADD SECURITY HEADERS
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    # No security headers set

SECURE CODE (✅):
    @app.after_request
    def set_security_headers(response):
        # Prevent MIME type sniffing
        response.headers['X-Content-Type-Options'] = 'nosniff'
        
        # Prevent clickjacking
        response.headers['X-Frame-Options'] = 'DENY'
        
        # Enable XSS protection in older browsers
        response.headers['X-XSS-Protection'] = '1; mode=block'
        
        # Force HTTPS (HSTS)
        response.headers['Strict-Transport-Security'] = 'max-age=31536000; includeSubDomains'
        
        # Content Security Policy
        response.headers['Content-Security-Policy'] = "default-src 'self'"
        
        return response

EXPLANATION:
- Security headers tell browser how to handle content
- X-Content-Type-Options: Prevent MIME type sniffing
- X-Frame-Options: Prevent clickjacking attacks
- X-XSS-Protection: Enable XSS filter in browsers
- Strict-Transport-Security: Force HTTPS
- Content-Security-Policy: Restrict resource loading

IMPLEMENTATION STEPS:
1. Add set_security_headers() function
2. Decorate with @app.after_request
3. Add all security headers
4. Test with browser dev tools (Network tab)
5. Verify headers are sent in responses

STEP 11: IMPLEMENT PROPER PASSWORD HASHING
═══════════════════════════════════════════════════════════════════════════════

VULNERABLE CODE (❌):
    # Storing plain passwords or weak hashing
    password = request.form.get('password')
    cursor.execute("INSERT INTO users (password) VALUES (?)", (password,))
    # Later:
    cursor.execute("SELECT * FROM users WHERE password=?", (password,))

SECURE CODE (✅):
    from werkzeug.security import generate_password_hash, check_password_hash
    
    # Registration:
    password = request.form.get('password')
    password_hash = generate_password_hash(password, method='pbkdf2')
    cursor.execute("INSERT INTO users (password_hash) VALUES (?)", (password_hash,))
    
    # Login:
    password_hash = cursor.execute("SELECT password_hash FROM users WHERE id=?", (user_id,))
    if check_password_hash(password_hash, provided_password):
        # Password is correct

EXPLANATION:
- Never store plain passwords
- Use strong hashing algorithms (pbkdf2, bcrypt, scrypt)
- Use check_password_hash() for comparison
- Werkzeug includes password hashing functions
- One-way hashing: can't reverse to get password

IMPLEMENTATION STEPS:
1. Change password column to password_hash
2. Hash password on registration: generate_password_hash()
3. Compare on login: check_password_hash()
4. Never output hashes (users don't need them)
5. Migrate existing passwords: hash on next login
